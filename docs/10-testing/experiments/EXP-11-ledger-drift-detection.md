> Status: **Approved** (Claude, delegated by the Owner for technical documents, 2026-11-01) · Updated: 2026-11-01 (P1-27: first version, the 20 corruptions listed, DR-321) · DOC-100 / EXP-11

> Main readers: P2-11 (the nightly check and this harness), P2-09 (void and the money log), the owners of `integrity_weekly` (DOC-27) and `integrity_notices` (DOC-31); the evaluation of NFR-09; the review of M2

The ledger has eight invariants (DOC-22 §3, I-1…I-8). Each is guarded by the write path, by a constraint or by a trigger; the nightly job `invariant_check` is the net under all of them: it must notice a state that none of the guards allowed but something produced (a bug, a hand edit, a restore gone wrong). This experiment **injects the twenty corruptions of DR-78**, plus the two table-level checks of DOC-15 §12.2, one at a time into a copy of realistic data, and requires that the check reports each of them, reports nothing else, reports nothing on clean data, repairs nothing, and costs little. It does not test the guards (LG-59, LG-60), the alert rule (`promtool`, P2-11) or the runbook (RB-01).

## 1. Hypothesis

| ID | Statement | Source | Measured by |

| H6 | A corruption in one building is reported for that building only | DR-244, ADR-0014 | C5 |
| H7 | A difference injected at any moment is reported **within 24 hours** | NFR-09 | C6 |

## 4. Baseline and ground truth

The injected corruptions are the negative cases of the experiment and the **clean data is its control** (DOC-89 §6). There is no second implementation of the check.

- **The truth is the injection.** The harness knows what it broke; the expected set is in §3; the report of the job is compared with it. The oracle never reads the table the job read: for C4 and C5 it reads digests.
- **Clean data is made by the product.** The `use-case building` is made only by the real use cases (`PublishFeeBatch`, `CreatePaymentIntent`, `settle()`, `RecordManualPayment`, `RecallFeeBatch`, `VoidPayment`, void of a charge), so the clean state is one the system can reach. The `bulk building` is generated by SQL with all triggers and constraints on, so it is valid by the database's own rules; it exists for the cost and for one more false-positive check, not for realism of history.

## 6. Steps and metrics

```bash
bun run exp:11 --seed-only        # once per host: the use-case building and the bulk building into the base database
bun run exp:11                    # five runs; K01…K22; clean control; cost; results/EXP-11-<utc>-run1…5.json and -summary.json
EXP_PART=inject bun run exp:11    # the nightly form: K01…K22 and C1, C2, C4, C5, C7 only
```

One run:

1. **Clean control.** Run `invariant_check` and both outside jobs on each building: rows per query, findings, gauge, and the digest of the ledger tables (`charge`, `charge_line`, `allocation`, `payment`, `receipt`, `document_counter`, `gateway_event`, `payment_intent`, `payment_intent_item`: `sha256` of `COPY … TO` ordered by id).
2. **Injection.** For `k` in K01…K22 (order shuffled with the seeded `Rng`): clone; inject `k` into building A (the second building B stays clean); run the job on A and on B; read the rows per query, the findings, the gauge; digest again; drop the clone.
3. **Detection within 24 h (C6).** On one clone, `FakeClock` at 03:01 building time; inject K08; advance to 02:59 the next day: no run has happened; advance to 03:00: the scheduler runs `invariant_check` and it reports K08; the time between injection and report is 23 h 59 m < 24 h. Repeat for K20 against the Monday 03:30 `integrity_weekly` (7 days: this job is weekly and reports within a week, which is its own contract and not NFR-09's 24 h; recorded as `weeklyDetectionHours`).
4. **Cost.** On the `bulk building` run `invariant_check` five times in a row (the first is a warm-up of the plan cache and counted); record `durationS` of each as the job's `job_run` duration.

| Name | Definition |
| --- | --- |
| `rows[Qnn]` | Rows returned by query `Qnn` for the corrupted building in one injection |
| `fired` | The set of queries (or the outside job's `kind`) with at least one row |
| `expected` | The set in §3 for the injection |
| `missing`, `unexpected` | `expected − fired` and `fired − expected` |
| `falsePositives` | Rows returned by any query, or findings by any job, on a clean building (the control and the second building) |
| `gauge` | `ledger_invariant_violations` after the job, and `rowsTotal` the sum of `rows[Qnn]` |
| `ledgerDigestBefore`, `After` | The `sha256` of §6 step 1 |
| `durationS` | The duration of one job run on the bulk building |
| `detectionHours` | `report time − injection time` on the `FakeClock` of step 3 |

## 7. Pass criteria

`correctness` criteria hold in every one of the five runs; `duration` in the median (DOC-89 §3).

| ID | Criterion | Kind |
| --- | --- | --- |
| C1 | For K01…K22, `fired` contains the primary query (or job kind) of §3: **22 of 22 reported** | correctness |
| C2 | For K01…K22, `missing` and `unexpected` are both empty (the set equals §3) | correctness |
| C3 | `falsePositives == 0` on the `use-case building`, the `bulk building`, and building B in every injection | correctness |
| C4 | `ledgerDigestBefore == ledgerDigestAfter` for every injection (the job repairs nothing) | correctness |
| C5 | For every injection in building A, building B's `rows` and findings are all 0 | correctness |
| C6 | `detectionHours < 24` for the ledger check; `weeklyDetectionHours <= 168` for the weekly job | correctness |
| C7 | `gauge == rowsTotal` after each injection and `gauge == 0` on clean buildings | correctness |
| C8 | `durationS <= 60` on the bulk building | duration (median) |

K01 and K04 must show the whole set of §3 (for K04 four queries); a query that stays silent where §3 expects it (for example Q10 for K04) is `missing` and fails C2 even though C1 holds.

**Worked reading.** In a run K08 injected into the bulk building returns `Q08` with 1 row; the digest before and after are equal; building B returns 0 everywhere; the gauge is 1. C1, C2, C4, C5 and C7 pass for K08. If K05 also fired `Q16`, `unexpected = {Q16}` and C2 fails: either §3 is wrong (a new version) or the query is.

## 10. Threats to validity

| Threat | Handling |
| --- | --- |
| The corruptions are injected with triggers off, as no real bug would do | They produce the **state** a bug would leave; what matters is that the check sees the state. The guards are LG-59 and LG-60 |
| The expected sets were measured on the same queries they judge | The sets were written from the meaning of each invariant (DOC-22 §3, I-1…I-8) and then checked against a run on 2026-10-26; a surprise is a finding about the document or the query, never a reason to edit the expectation silently |
| 22 injections are a list, not a space: a 23rd kind of drift may exist | The nightly check is the net for **known** drift; unknown drift is why the first production month recalibrates (DOC-10 §9) and why RB-01 is a procedure, not a patch |
| The bulk building is generated by SQL, so its history is unrealistic | It is used for cost and for a second control only; the `use-case building` is the realistic control |
| The outside jobs are weekly and the injection runs them on demand | The on-demand run uses the same job code; the schedule is the job catalog's (DOC-38 §4.1) and C6 checks its period |
| The clone approach hides a lock or snapshot effect of a job running against a live database | LG-58 tests the `REPEATABLE READ` snapshot while a payment commits |
