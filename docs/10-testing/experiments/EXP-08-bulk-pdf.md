# EXP-08: Bulk fee notices fit the time and the memory of the staging host

> Status: **Approved** (Claude, delegated by the Owner for technical documents, 2026-11-01) · Updated: 2026-11-01 (P1-27: first version, DR-320) · DOC-97 / EXP-08
> Depends on: [common protocol](README.md) (DOC-89), original SDD §20.2, [DR](../../00-decision-register.md) (DR-06, 56, 78, 120, 244, 245, 291, 293, 294, 318, 320), [DOC-34](../../06-design/pdf-rendering.md) §4, §8, §9, §15, §16.3, [DOC-03](../../01-product/requirements.md) (NFR-05, FR-36.4, FR-36.5), [DOC-10](../../03-architecture/quality-attributes.md) §4.2, §6.1, [DOC-41](../../06-design/configuration-reference.md) (`PDF_*`), [DOC-38](../../06-design/jobs-and-outbox-runtime.md) §4.1
> Main readers: P2-13 (PDF rendering: the experiment is its acceptance), the evaluation of NFR-05; the review of M2

DOC-34 plans to render 240 fee notices in about 40 s and 5,000 in about 14 minutes on the staging host, in render-host child processes that are replaced every 150 documents so that the renderer's slow memory growth stays under a limit. Those are planned figures. This experiment makes the real bulk job (`fee_notice_run`, E-99) run on the staging host and measures the wall time and the memory of the worker container, and checks that what came out is usable. It does not test one notice's layout or text (the `PD-` tests), the cache keys (PD-01…), the resume after a kill (PD-28), or a production-size host.

## 1. Hypothesis

| ID | Statement | Source | Measured by |
| --- | --- | --- | --- |
| H1 | **240 units** (cold cache, 1 render host) finish in **≤ 2 minutes** from the request to `ready`, in Vietnamese, English and bilingual | NFR-05, FR-36.4 | C1 |
| H2 | **5,000 units** (cold cache, bilingual: the largest document) finish in **≤ 30 minutes** | NFR-05, FR-36.4 | C2 |
| H3 | The **worker container** never uses more than **1 GB** of memory, in any case | NFR-05, FR-36.4, DR-291 | C3 |
| H4 | The output is usable: every unit has a PDF that opens, the manifest lists every unit `ok`, the ZIP is valid, and the text of sampled PDFs holds the owner's name and the charge total | FR-36.5, DOC-34 §9 | C4, C5, C6 |
| H5 | The cache works: a second request for the same batch renders nothing (every unit is a hit) and is not slower than the first | DR-244, DOC-34 §8.1 | C7 |
| H6 | The render hosts are recycled as designed: restarts happen and no render exceeds its 30 s limit or fails | DR-291, DOC-34 §4.1 | C8 |

## 3. Baseline

None. EXP-08 measures against a budget, not against an alternative (DOC-89 §6). DOC-34 §15.2 holds the first-step smoke measurement of a single in-process renderer, which exceeded 1 GB at 720 documents; it is the reason for the render-host design (DR-291) and is not repeated here. If a case misses its limit, DOC-34 §15.1 fixes the order of the fallbacks: lower `PDF_RENDERER_MAX_DOCUMENTS`, then the same renderer under Node, then Typst (DR-56); each is a new DR and a new set.

## 5. Steps

```bash
# on the staging host, as the deploy user
bun run exp:08 --seed-only           # once: the scratch building, 5,000 units, the two batches
bun run exp:08                       # one warm-up pass, five runs of cases A…E, the result files and the summary
```

For each case, the script:

1. For a cold case: delete the batch's rows in `finance.fee_notice_pdf`, the files they point to, and the batch's earlier `fee_notice_job` rows and ZIPs.
2. Start the sampler: every 1,000 ms read `memory.current` and `memory.stat` (`anon`, `file`) of the worker's cgroup (`/sys/fs/cgroup/.../memory.*`) and the sum of `VmRSS` of the worker and its render hosts; at the end read `memory.peak`.
3. `POST /staff/fee-batches/{id}/pdf {language}` (E-99). Record `t0` on `performance.now()`.
4. Poll E-177 every 2 s until `ready` or `failed`; record the job's `created_at` and `finished_at`.
5. Stop the sampler. Download the ZIP with the signed URL.
6. Check the output (§6, C4…C6): `unzip -t`; count entries; read the manifest; `pdfinfo` on every PDF (or `qpdf --check` when `pdfinfo` is missing); `pdftotext` on the first, the last and 10 random PDFs (picked with the seeded `Rng`) and look for the owner's name and the charge total.
7. Write the case's metrics into the run file.

## 6. Metrics and formulas

| Name | Definition |
| --- | --- |
| `durationS` | `finished_at − created_at` of the `fee_notice_job` row, in seconds: the claim tick (≤ 5 s), the render phase and the ZIP phase. The wall time seen by the client (`t0` to the poll that saw `ready`) is also recorded as `clientS` (≥ `durationS`, within the 2 s poll) |
| `memoryPeakBytes` | `memory.peak` of the worker container's cgroup over the case (includes the render hosts and the page cache the container touched) |
| `anonPeakBytes` | The highest sampled `anon` of `memory.stat`: memory that cannot be reclaimed. Reported beside the peak, because a page cache can raise `memory.peak` without being a leak |
| `rssPeakMb` | The highest sampled sum of `VmRSS` of the worker and its hosts, in MB (1 MB = 1,048,576 bytes) |
| `cpuS` | `usage_usec` of the cgroup `cpu.stat` over the case, in seconds |
| `rendered`, `cacheHits` | Documents rendered and documents found in the cache, from the job's log line `fee_notice.ready` |
| `restarts` | `pdf_renderer_restarts_total` over the case, by reason (`documents`, `rss`, `timeout`, `crash`) |
| `failedUnits` | Units with `failed` in the manifest |
| `pdfOpenFailures` | PDFs that `pdfinfo` cannot open |
| `zipEntries` | Entries of the ZIP; expected `units + 1` (the manifest) |
| `zipBytes` | Size of the ZIP |
| `textMisses` | Sampled PDFs (12 per case) whose text lacks the owner's name or the total in the format of DOC-34 §6 |

1 GB in NFR-05 is read strictly as **10^9 bytes** (not 1 GiB), so a pass means a pass under either reading.

## 7. Pass criteria

`correctness` criteria hold in **every run**; `duration` and `memory` criteria hold in the **median of the five runs** (DOC-89 §3). The summary adds a warning when a `max` is above 1.5 × its limit.

| ID | Case | Criterion | Kind |
| --- | --- | --- | --- |
| C1 | A, B, C | `durationS <= 120` | duration (median) |
| C2 | D | `durationS <= 1800` | duration (median) |
| C3 | A…E | `memoryPeakBytes <= 1_000_000_000` in the median; and below the worker's `mem_limit` (1.5 GB) in every run, since a kill by the limit is a failed run | memory (median) |
| C4 | A…E | `failedUnits == 0` and every manifest line is `ok` | correctness |
| C5 | A…E | `zipEntries == units + 1`, `unzip -t` passes, `pdfOpenFailures == 0` | correctness |
| C6 | A…E | `textMisses == 0` | correctness |
| C7 | E | `rendered == 0`, `cacheHits == 5000`, and `durationS(E) <= durationS(D)` | correctness |
| C8 | D | `restarts{reason="documents"} >= floor(5000 / 150) − 1` (the hosts were recycled), `restarts{reason="timeout"} == 0`, `restarts{reason="crash"} == 0` and `attempts == 1` | correctness |

`anonPeakBytes` and `rssPeakMb` have no criterion: they explain `memoryPeakBytes` when C3 fails. A case that misses its limit fails the experiment; the fallback order of §3 applies.

**Worked reading.** Case D in a run took 842 s (14 min), `memory.peak` 640 MB, `anon` peak 410 MB, 32 restarts for `documents`, 0 failed units, 5,001 ZIP entries, 12 of 12 text samples found: C2, C3, C4…C6 and C8 pass for this run. Over five runs the median duration is 851 s and the maximum 903 s, below 1.5 × 1,800: no warning.

## 10. Threats to validity

| Threat | Handling |
| --- | --- |
| A quiet host is not a real one: in production the worker also runs the other jobs while a Manager asks for 5,000 notices | The request is a background job with bounded concurrency (DR-291); the other jobs are light; a run during the `nightly` window is not part of this set |
| `memory.peak` includes the page cache of the ZIP parts and the PDFs read back, which the kernel can reclaim | `anonPeakBytes` is reported with it; C3 uses the stricter number, so a pass is a pass under both |
| Generated owner names and amounts are not the building's | The seed uses the full Vietnamese diacritics and a spread of amounts, and the layout does not depend on the name beyond its length |
| The cases for 5,000 units in `vi` and `en` are not run | `both` is the longest document and the heaviest; a shorter document is bounded by it. If this proves wrong, a case is added in a new version (DOC-89 §9) |
| SeaweedFS and PostgreSQL share the host, so their load shows in the time | Intended: the production host is the same shape (DR-06); the CPU of the cgroup is reported separately |
| The host is the VPS of one provider and one day | The set is repeated when the host's size changes (a change of `vCPU` or `mem_limit` raises the experiment's `version`) |
